OPERATING SYSTEMS INTERACTIVE GUIDE — SECTION AUTHORING CONTRACT
=================================================================

WHAT WE ARE BUILDING
--------------------
One self-contained HTML file (no network, no CDN, works offline from a USB stick) that teaches
the first five chapters of an undergraduate operating-systems course (40 sections, following the
course outline: computer system overview, OS overview, processes, threads, concurrency). Each section is one JavaScript file, sections/<id>.js, that calls Guide.section({...}).
build.mjs stitches the shell + chapters.js + every section into ../operating-systems-ch1-5.html.

AUDIENCE: first/second-year college students with ZERO operating-systems background. They may be
seeing words like "register", "interrupt", "cache" or "process" for the first time. The goal is that
every concept becomes crystal clear. Write like the best tutor they ever had: warm, direct, precise,
never condescending, never hand-wavy. Short sentences. Define every term the first time it appears.
Concrete examples and numbers beat abstractions. Explain WHY things are designed the way they are.

ORIGINALITY + WRITING PROTOCOL (read carefully — violating this makes your work fail)
------------------------------------------------------------------------------------
* Write every sentence in YOUR OWN WORDS, as an original teacher designing an original lesson.
  Do not try to recall, quote or closely paraphrase any textbook's wording, tables or figures, and do
  not mention any textbook. Facts, standard terminology, algorithm names and well-known classic
  examples are fine; explain them with your own sentences, your own analogies and your own structure.
* NEVER emit the whole section file in one tool call. Large single outputs fail. Build it in pieces:
    1. Write a skeleton (about 60–120 lines): the Guide.section({...}) call with id, title, short,
       summary, objectives, terms, css, a steps array that contains only the marker comment
       /*STEPS*/ , and notes: `/*NOTES*/`.
    2. Add ONE step per Edit call, inserting it just before the /*STEPS*/ marker (keep each edit
       under roughly 200 lines; split a very large step's helper code into its own earlier edit).
    3. Write the notes in one or two separate Edit calls that replace /*NOTES*/.
    4. Remove the markers at the end. Run node build.mjs --section <id> after every two or three
       steps so syntax errors are caught early.

THE FILE CONTRACT
-----------------
sections/<id>.js contains exactly one call:

Guide.section({
  id: '3.2',                 // must equal the file name
  title: 'Process States',   // exact section title from your brief
  short: 'Process states',   // optional short label (<= 24 chars) for tight spaces
  summary: 'One sentence, <= 110 chars, shown in the chapter map.',
  objectives: ['3–5 "you will be able to ..." outcomes'],
  terms: [['Term (ABBR)', 'Plain-language definition, 1–2 sentences.'], ...],   // 8–20 terms
  css: `.sec-3-2 .whatever { ... }`,   // OPTIONAL; EVERY selector MUST start with .sec-<major>-<minor>
  steps: [ { title, kind, html | render | quiz }, ... ],                     // 6–10 steps
  notes: `<h3>...</h3><p>...</p>...`,  // static study notes (see NOTES below)
});

Plain modern JavaScript (ES2020). No imports, no fetch, no external URLs, no fonts, no images from the
web, no localStorage of your own, no alert/confirm/prompt, no position:fixed, no global variables
(wrap helpers inside the Guide.section call or an IIFE). Never write the text "</script>" or "<!--".
No emoji (they print as black boxes in the PDF). Unicode arrows/symbols such as → ← ↑ ↓ ⇒ ✓ ✗ × ≤ ≥ ≈ Σ
are fine. Never mention Keiser, a course code, grading, points, rubrics, or time estimates.
Write original explanations only (see ORIGINALITY above). Well-known classic examples (e.g. the
hypothetical accumulator machine program, the echo procedure, Dekker's attempts) are fine to recreate
in your own presentation. Do not cite any book, figure, table or page number; the guide stands alone.

STEP OBJECT
-----------
  title:  short headline (<= 60 chars) shown in the step header
  kind:   'story' (Big Picture) | 'learn' | 'explore' | 'lab' | 'predict' | 'compare' | 'recap' | 'check'
  html:   string of HTML (static content)           ┐ html runs first, then render may
  render: function (el, ctx) { ... }                 ┘ enhance it; render may return a cleanup fn
  quiz:   [questions]  → the shell renders a full quiz UI into the step (use kind:'check')
  core:   true  (optional) → this step is on the shorter "core path" route. The core path automatically
          keeps each section's first step, its recap and its quiz; flag the 1–2 essential hands-on steps.
Keyboard: arrow keys inside ctx.ui.tabs, ctx.ui.seg and any element with role tablist/radiogroup/
listbox/slider or a data-keys attribute are NOT used for slide navigation, so custom widgets that
need arrow keys should carry data-keys. Quiz answers persist automatically (localStorage).

THE CANVAS: THE MOST IMPORTANT LAYOUT RULE
------------------------------------------
Every step body is EXACTLY 1152 px wide × 540 px tall (the shell scales it to fit the screen).
NOTHING MAY SCROLL OR OVERFLOW. If content does not fit, split it into two steps, tighten wording, or
use tabs (ctx.ui.tabs) — never shrink text below 13 px and never rely on scrolling. The only allowed
internal scrolling is a small log/trace panel (class "log" or "scroll-y") whose overflow is expected.
Base font is 17px. Use h3 (20px) for in-step headings, .lead (19px) for an opening sentence,
.small (14.5px) for secondary text, .xs (12.5px) only for labels.
Top-level layout helpers: .split (2 cols), .split.l (5fr/7fr), .split.r (7fr/5fr), .split.l3, .split.r3,
.grid-2/.grid-3/.grid-4, .stack (vertical flex, gap 12), .row (wrapping flex), .fill (height 100%),
.grow (flex:1). A typical explore step: <div class="split l fill"> text left, interactive right.
On phones (narrow mode) the shell stacks .split/.grid columns and lets the page scroll, so
keep layouts built from those helpers and give SVGs a viewBox with width="100%".

THE ctx OBJECT (second argument to render)
------------------------------------------
  ctx.h(tag, props, ...children)   DOM builder; props: class, style{...}, html, text, onclick/oninput..., any attr
  ctx.s(tag, props, ...children)   same for SVG elements
  ctx.frag(htmlString)             DocumentFragment
  ctx.$(sel) / ctx.$$(sel)         query inside this step
  ctx.every(ms, fn) ctx.after(ms, fn) ctx.sleep(ms) ctx.raf(fn) ctx.on(target, ev, fn)
                                   ALL auto-cancelled when the student leaves the step. Use these
                                   instead of setInterval/setTimeout/addEventListener on window/document.
                                   In async code, check ctx.alive after every await.
  ctx.toast(msg)                   small message at the bottom
  ctx.narrow                       true on phones (layout is stacked)
  ctx.util: clamp, range(n), shuffle(arr), seeded(seed)->rng, fmt(num, digits), esc(str)
  ctx.refit()                      re-run the overflow check after you change layout
  ctx.ui.player({count, render(i) → captionHTML, interval, autoplay, speed:false, captionBelow, onStep})
        Step-through controller (restart / back / play-pause / next / speed). render(i) must redraw
        state i FROM SCRATCH (deterministic) and return the narration for that frame. Build your visuals
        before creating the player (it calls render(0) immediately). Methods: go(i) next() prev() reset()
        play() stop() setCount(n) refresh(); .el is the element to append.
  ctx.ui.slider({label, min, max, step, value, format(v), onInput(v)}) → element (.set(v, fire) .get())
  ctx.ui.seg(options, value, onChange)  segmented toggle; options: ['a','b'] or [{value,label}] (.set .get)
  ctx.ui.tabs([{label, html | render(panel) }], {initial, onChange}) → element filling its parent
  ctx.ui.reveal(buttonLabel, htmlOrNode) → click-to-reveal block (great for "predict, then check")
  ctx.ui.flipcards([[frontHTML, backHTML], ...], {cols, height}) → grid of flip cards
  ctx.ui.code(source, {lang:'c'|'plain', nums:true, fontSize, maxHeight}) → <pre> with syntax colouring;
        .mark(lineNumbers, cls='cur'|'ok'|'bad'|'dim') .clear() .line(n)
  ctx.ui.quiz(questions, {key}) → embed a mini quiz anywhere (the check step does this for you)

QUIZ QUESTIONS (for kind:'check' steps: { title, kind:'check', quiz:[...] })
----------------------------------------------------------------------------
Every question needs q (HTML) and why (HTML explanation that TEACHES, 1–3 sentences).
  mc     { q, choices:[...], answer: index, feedback:[one per choice, null for the right one], why }
  tf     { type:'tf', q, answer: true|false, why }
  multi  { type:'multi', q, choices:[...], answer:[indices], why }
  order  { type:'order', q, items:[...IN THE CORRECT ORDER...], why }        (shuffled for the student)
  match  { type:'match', q, pairs:[[left, right], ...], why }                (right values unique)
  bucket { type:'bucket', q, buckets:['A','B'], items:[[text, bucketIndex], ...], why }
  num    { type:'num', q, answer: number, tol: absoluteTolerance, unit:'µs', why }
  optional: hint, code (shown as a code block under the question)
Write 8–12 questions per section using at least 4 different types. Include numeric (num) questions
whenever the section has formulas or quantities. MC feedback must explain why each wrong choice is
wrong. Distractors must be plausible misconceptions, never silly, and never ambiguous.
The chapter challenge and final challenge reuse these questions, so each must stand alone
(do not write "in the simulation above").

TEACHING DESIGN (what every section must have)
----------------------------------------------
6–10 steps, roughly in this arc:
 1. Big Picture (kind 'story'): what problem this section solves and why anyone cares, a vivid analogy,
    and a preview of what the student will be able to do. Often includes a small clickable diagram.
 2–N. One idea per step (kinds learn / explore / lab / predict / compare). Most of these must be
    GENUINELY interactive (render): the student changes something (clicks a part, drags a slider,
    chooses the next process to run, steps through time, toggles a policy) and immediately SEES the
    consequence, with narration that says what happened and WHY. Minimum: 3 interactive steps; large,
    mechanism-heavy sections (instruction execution, interrupts, cache, process states, semaphores,
    Dekker/Peterson, monitors, readers/writers, ULT vs KLT, Amdahl) should have 5+.
    Great interaction patterns:
      • step-through simulation with ctx.ui.player and a narrated caption per frame
      • "you are the scheduler/the CPU": the student chooses what happens next; the sim shows the
        result (race condition, deadlock, livelock, violated mutual exclusion...) and explains it
      • sliders that drive a live formula/graph (hit ratio, Amdahl, utilization, availability)
      • clickable diagram hotspots that explain each component
      • predict-then-reveal: ask a question, let the student commit, then show the answer and why
      • sort/classify mini-games with immediate feedback
      • compare modes side by side (with vs without interrupts, ULT vs KLT, Hoare vs Mesa monitor)
    Every code or pseudocode listing shown to students must have a plain-language comment on EVERY
    line (who/what/when/why), or a side-by-side "what this line does" explanation that highlights in
    sync. Use the standard names (semWait, semSignal, cwait, csignal, compare_and_swap, fork...).
    Include "Common mistake" (callout warn) and "Why it matters" (callout why) callouts where they help.
 N-1. Recap (kind 'recap'): the 4–6 things to remember, e.g. flip cards or a compact visual summary.
 N. Check Yourself (kind 'check'): the quiz.
ACCURACY: use the standard terminology, models, lists and numbers given in your coverage brief
(these are the names students meet in their course). When the brief gives a list (e.g. the 5
process-creation steps, the 7 process-switch steps, the 6 mutual-exclusion requirements), teach the
full list in order with those names, explained in your own words. If unsure of a detail, prefer the
standard, widely-taught formulation and keep claims precise rather than vague. Numbers inside
simulations must be internally consistent (check your arithmetic).

NOTES (the static study notes; shown in the Notes drawer and printed in the PDF study guide)
------------------------------------------------------------------------------------------
Plain HTML (no script, no .t spans needed): h3/h4, p, ul/ol, table, pre, small inline SVG allowed
(use explicit light colours in notes SVG, e.g. fill="#e1eaff" stroke="#2563eb", since print is light).
3,000–8,000 characters, in your own words. A complete, well-organised summary of EVERYTHING the section teaches: every
definition, list, formula (with a worked example), model and comparison, in the same order as the steps.
Someone who only reads the notes must be able to answer every quiz question.
