Problem 1Races and the rules a lock must follow

A statement such as count = count + 1 is not one action. The processor runs it as three steps: load (copy count from memory into one of the thread's own registers), compute (change the register), and store (copy the register back into count). Each thread has its own registers. The scheduler can switch from one thread to another between any two steps, but never in the middle of one.

(a) (i) count starts at 3. Thread T0 runs count = count + 1 once and thread T1 runs count = count * 2 once. List every value count can hold after both have finished, and for each value give one order of the six steps that produces it (for example: T0 load, T0 add, T1 load, ...). (ii) count starts at 0, and each of two threads runs count = count + 1 four times. What are the largest and the smallest possible final values? The values alone are not the answer (Part B's program can confirm them): the answer is an order of steps that produces the smallest, step by step, and an explanation of why no order can produce anything smaller.

The six requirements any mutual exclusion scheme must meet:

  1. Only one process inside: at most one process at a time is in its critical section for a resource.
  2. Halting outside must not hurt others: a process that stops in its non-critical code must not stop the others from entering.
  3. No deadlock and no starvation: a process that wants to enter is never delayed forever.
  4. Free means enter at once: if nobody is inside, a process that asks to enter gets in without delay.
  5. No assumptions about speed or processors: the scheme works whatever the relative speeds and however many processors there are.
  6. Stay inside for a finite time: a process leaves its critical section after a finite time.

(b) Each scheme below is flawed. Name the requirement (1 to 6) that is the root cause of its trouble, and explain in one or two sentences.

(c) A kernel protects its run queue by disabling interrupts on entry to the critical section and enabling them again on exit. (i) Why does this guarantee mutual exclusion on a computer with one processor? (ii) Give two costs of the approach, even on one processor. (iii) The same kernel is moved to a computer with four cores. Describe exactly how two threads can now be in the critical section at the same time.

compare_and_swap(word, testval, newval) is one machine instruction, so it cannot be interrupted: it reads *word, writes newval into it only if the value read equals testval, and returns the value it read. A spin lock built on it:

int bolt = 0;                                  /* shared: 0 = free, 1 = taken */
while (compare_and_swap(&bolt, 0, 1) == 1)
    ;                                          /* spin until the lock was free */
/* critical section */
bolt = 0;                                      /* release */

(d) (i) What does the call return, and what does it change, when bolt is 0 and when it is 1? Use scheme F from (b) to explain why the read and the write must happen in one instruction. (ii) On a four-core machine, P1 is inside its critical section while P2, P3 and P4 spin. P1 leaves and soon asks to enter again. Which process gets in next, and can P4 wait forever? Which requirement is at risk? (iii) On a one-processor machine with strict priorities, low-priority L holds bolt when high-priority H becomes ready and starts spinning on it. What happens, and why?

Problem 2Semaphores, readers and writers, and messages

A producer P and a consumer C share a buffer with room for 2 items, guarded by three semaphores: s (one process at a time in the buffer), n (items waiting) and e (empty slots).

/* producer P */                    /* consumer C */
while (true) {                      while (true) {
    v = produce();                      semWait(n);
    semWait(e);                         semWait(s);
    semWait(s);                         w = take();
    append(v);                          semSignal(s);
    semSignal(s);                       semSignal(e);
    semSignal(n);                       consume(w);
}                                   }

Semaphores work as in the chapter: semWait subtracts 1 and, if the value is now negative, blocks the caller; semSignal adds 1 and, if the value is still zero or negative, releases one blocked process. So a negative value counts the processes waiting.

(a) The buffer already holds item A, so s = 1, n = 1 and e = 1. The twelve operations below run in this order. After each one, write the values of the three semaphores, the items in the buffer (oldest first), and which process is blocked and on which semaphore (or "none").

(b) A programmer swaps the producer's two waits, so it runs semWait(s) and then semWait(e). (i) Start with a full buffer: s = 1, n = 2, e = 0. Give the shortest sequence of semaphore operations that leaves both processes blocked forever, with each semaphore's value after every operation. Who holds what, and who is waiting for whom? (ii) If the buffer is not full when the two processes start, can they still end up in the same deadlock later? How? (iii) Would swapping the producer's two semSignal calls instead cause the same problem? Why or why not?

Readers may share a file; a writer needs it alone. Each reader reads for 4 time units and the writer writes for 2. Arrivals: R1 at time 0, W1 at time 1, R2 at 2, R3 at 5, R4 at 8. Nobody else arrives.

  • Readers priority: only the first reader to arrive while nobody is reading has to wait for the file; any reader that arrives while others are reading goes straight in. The writer starts only when no one is reading.
  • Writers priority: once a writer is waiting, no new reader may start until no writer is waiting or writing; readers already reading finish normally.

(c) Give each start and finish time under both policies.

Mutual exclusion with a mailbox. receive blocks until a message is there; send never blocks.

create_mailbox(box);
send(box, null);              /* done once, before any process starts */
/* every process: */
while (true) {
    receive(box, msg);
    /* critical section */
    send(box, msg);
    /* remainder */
}

(d) (i) What does the single message stand for, and why can at most one process be in its critical section? (ii) What happens if the mailbox starts with two messages, and what if it starts with none? (iii) Why would the scheme fail if receive returned at once, empty-handed, when the box is empty?

Problem 3Records, blocks and organizations

(a) (i) Fixed blocking. A file holds 10,000 records of 300 bytes each, in blocks of 2,048 bytes. Records are never split. Give the blocking factor, the unused bytes at the end of each full block, the number of blocks the file needs, and the block and slot of record number 4,321 (records, blocks and slots are all numbered from 0). What percentage of all the bytes in the file's blocks holds no record data? Count the unused bytes in every block, including the space left at the end of the last block.

(ii) Variable-length records. Eight records are written in this order into blocks of 1,024 bytes: A 300, B 500, C 450, D 200, E 700, F 350, G 600, H 400 (sizes in bytes). Ignore any space taken by pointers or headers. Pack them both ways.

(b) Choose a file organization for each job: pile, sequential, indexed sequential, indexed, or direct (hashed). Use each one once, and say why it fits better than the others.

B-trees in this problem follow the chapter's rules for a tree of minimum degree d: every node holds at most 2d − 1 keys; every node except the root holds at least d − 1 keys; a node with k keys that is not a leaf has k + 1 children; all leaves are on the same level. Insertion works top-down: on the way down from the root, every full node met (including the root, and including the leaf) is split before going further. A split moves the full node's middle key up into its parent and leaves the keys on each side in two separate nodes; splitting the root creates a new root, which is the only way the tree grows taller.

(c) (i) Insert these keys, in order, into an empty B-tree with d = 2 (so a node holds 1 to 3 keys): 50, 20, 80, 10, 30, 60, 90, 70, 40, 25, 35. Say which insertions cause splits and which key moves up each time, and draw the final tree level by level, for example [40] / [10 20] [60 80]. (ii) A B-tree with d = 50 holds 1,000,000 keys. How many keys can one node hold at most, and at least (if it is not the root)? Using the height bound h ≤ logd((n + 1) / 2), what is the most nodes a search can read? How many levels would the shortest possible binary search tree of the same keys have?

How many data blocks, and how many bytes, can be reached through each kind of pointer, and what is the largest possible file, in bytes and in GiB (two decimal places)?

(b) A file is 50 blocks long (blocks 0 to 49). For each allocation method, count disk reads: to reach block 30 on its own (with nothing in memory except the directory entry), on average over all 50 blocks, and to read the whole file in order once.

B2The starter program

Testing a lock by running real threads proves very little: a bad interleaving may need the scheduler to switch at one exact instruction, and that can happen once in a million runs, or never on your computer. This program does the opposite. It writes each thread as a short list of atomic steps and then tries every order in which the two threads' steps could run.

  • A thread is a list of steps numbered 0, 1, 2, .... Each step is a pair: a text such as "flag[me] = True" and a small function that does it. The function gets the shared variables (a dictionary called sh) and the thread's number me (0 or 1, so the other thread is 1 - me). It returns the number of the step the thread runs next. Returning its own number makes the thread spin on that step (busy waiting); returning None means the step cannot happen yet, so the thread is blocked (that is how semWait on a zero semaphore is written). A step whose text starts with CS: is inside the critical section.
  • A state is everything that matters at one moment: each thread's next step number plus the value of every shared variable. From each state, each thread that can move gives one next state. The program visits every reachable state once, breadth first (all states one step from the start, then all states two steps away, and so on), so the first time it finds a bad state it has found the shortest interleaving that leads there, and it prints that interleaving.
  • For every model it reports: can both threads be in the critical section at once? and can every reachable state still finish? A state that cannot reach "both threads finished" by any order of steps is stuck: a deadlock (both blocked) or a spin that can never end. For the stuck case it also prints what each thread is doing there forever.
What "can always still finish" means. From every reachable state there is at least one order of steps that lets both threads finish. It says nothing about which order the scheduler actually picks. A scheduler is fair if it gives every thread that can move a turn sooner or later.
Why the output is the same on every computer: nothing is random and nothing depends on timing. The program lists every interleaving in a fixed order, so your output should match a classmate's line for line once both programs are correct.

Read it from top to bottom first; every line carries a comment. The semaphores in Experiment 3 never go below 0: semWait simply cannot happen while the value is 0. The chapter's version lets the value go negative to count the waiting processes, but which steps can happen next is the same, so the checker finds the same problems.

mutex.py
"""mutex.py: try every order in which two threads' steps can run, and report what can go wrong.

Run it from a terminal in the folder that holds this file:
    python mutex.py           (Windows)   or   python3 mutex.py   (macOS / Linux)

Your work is marked with TODO. Everything else already works: run the file before you change
anything; each experiment that reaches an unwritten TODO says which one and the rest still run.
Nothing here is random and nothing depends on timing. The program lists EVERY interleaving of the
two threads, so the output is the same on every computer and every run.
"""

from collections import deque  # a queue with fast removal from the front: the to-do list of the search

INCREMENTS = 3  # Experiment 1: how many times each thread adds 1 to count
VISITS = 2  # Experiment 2: how many times each thread passes through its critical section
SIZE = 2  # Experiment 3: how many items the bounded buffer can hold
ITEMS = 3  # Experiment 3: how many items the producer makes (and the consumer takes)


class NotWrittenYet(Exception):  # a custom error the starter raises wherever a TODO has not been written yet
    pass  # it needs no extra behavior; its name and message say everything


# ---------------------------------------------------------------------------
# How a thread is written down
#   A thread's program is a list of steps, numbered 0, 1, 2, ... Each step is a pair (text, action).
#   The action is a function action(sh, me). sh is a dictionary holding the shared variables (the
#   action may change it); me is this thread's number, 0 or 1, so the other thread is 1 - me.
#   The action returns the number of the step this thread runs next, or None when the step cannot
#   happen yet (the thread is blocked; the action must then leave sh unchanged).
#   A thread whose next step number equals the length of its program has finished.
#   A step whose text starts with "CS:" is inside the critical section.
#   One step is one atomic action: the other thread can run between two steps, never inside one.
# ---------------------------------------------------------------------------
def put(sh, name, value, nxt):  # a helper for actions that assign: sh[name] = value, then go to step nxt
    sh[name] = value  # the assignment
    return nxt  # the number of the step that runs next


def again(sh, me, first, done):  # the last step of a loop: count one pass, then go round again or finish
    sh[f"left{me}"] -= 1  # one pass fewer left for this thread (left0 belongs to thread 0, left1 to thread 1)
    return first if sh[f"left{me}"] > 0 else done  # back to step `first` while passes remain, else to step `done`


def sem_wait(name, nxt):  # builds a semWait step on the semaphore called `name`, followed by step nxt
    def action(sh, me):  # what the step does when the thread tries to take it
        if sh[name] == 0:  # no unit is available...
            return None  # ...so the thread is blocked here, and nothing changes
        sh[name] -= 1  # take one unit
        return nxt  # and carry on
    return (f"semWait({name})", action)  # the step: its text and its action


def sem_signal(name, nxt):  # builds a semSignal step on the semaphore called `name`, followed by step nxt
    return (f"semSignal({name})", lambda sh, me: put(sh, name, sh[name] + 1, nxt))  # give one unit back; never blocks


def append_item(nxt):  # builds the producer's critical-section step: one more item in the buffer
    return ("CS: append an item", lambda sh, me: put(sh, "items", sh["items"] + 1, nxt))  # items counts what the buffer holds


def take_item(nxt):  # builds the consumer's critical-section step: one item fewer in the buffer
    return ("CS: take an item", lambda sh, me: put(sh, "items", sh["items"] - 1, nxt))  # the item leaves the buffer


# ---------------------------------------------------------------------------
# The checker: a breadth-first search over every state the two threads can reach
#   A state = (each thread's next step number, the values of every shared variable).
# ---------------------------------------------------------------------------
def freeze(sh):  # turns the shared dictionary into a tuple, because only unchangeable values can go in a set
    return tuple(sorted(sh.items()))  # e.g. (("flag0", True), ("flag1", False), ("turn", 1))


def explore(threads, init):  # visits every reachable state; returns how each was first reached, and every move
    start = ((0,) * len(threads), freeze(init))  # both threads at step 0, shared variables at their starting values
    came_from = {start: None}  # for each state seen: (the state before it, the thread that moved); None for the start
    moves = {}  # for each state: the list of states one step away
    queue = deque([start])  # states whose moves have not been tried yet
    while queue:  # until every reachable state has been expanded
        state = queue.popleft()  # oldest first, so every state is first reached by a shortest path
        pcs, frozen = state  # the step numbers and the shared variables
        moves[state] = []  # filled in by the loop below
        for t, program in enumerate(threads):  # let thread 0, then thread 1, try its next step
            if pcs[t] == len(program):  # this thread has finished...
                continue  # ...so it has no step to take
            sh = dict(frozen)  # a fresh, changeable copy of the shared variables
            nxt = program[pcs[t]][1](sh, t)  # run thread t's next step on that copy
            if nxt is None:  # the step is blocked...
                continue  # ...so thread t cannot move in this state
            new = (pcs[:t] + (nxt,) + pcs[t + 1:], freeze(sh))  # the state after the step
            moves[state].append(new)  # remember the move
            if new not in came_from:  # a state never seen before...
                came_from[new] = (state, t)  # ...remember how we got there
                queue.append(new)  # ...and expand it later
    return came_from, moves  # the keys of came_from are all the reachable states, in the order they were found


def trace(came_from, threads, end):  # the moves that lead from the start to state `end`
    steps = []  # collected backwards, from `end` to the start
    while came_from[end] is not None:  # only the start has no previous state
        before, t = came_from[end]  # the state before, and the thread that moved
        steps.append((t, threads[t][before[0][t]][0], end[1]))  # (thread, text of the step it took, shared variables after)
        end = before  # one step further back
    return steps[::-1]  # reversed, so the first move comes first


def show(steps):  # prints a trace, one line per step
    for t, text, frozen in steps:  # every move in order
        shared = "  ".join(f"{k}={v}" for k, v in frozen if not k.startswith(("left", "reg")))  # the shared variables, minus loop counters and registers
        print(f"      T{t}  {text:<42} {shared}")  # e.g. "T0  flag[me] = True    flag0=True  flag1=False"


def status(threads, state):  # describes what each thread is doing in a state, e.g. "T0 blocked at semWait(e)"
    words = []  # one description per thread
    for t, program in enumerate(threads):  # each thread
        pc = state[0][t]  # its next step number
        if pc == len(program):  # past its last step
            words.append(f"T{t} has finished")  # nothing left to do
            continue  # next thread
        sh = dict(state[1])  # a copy of the shared variables to try the step on
        nxt = program[pc][1](sh, t)  # try the step
        if nxt is None:  # the step cannot happen
            how = "is blocked at"  # waiting inside the OS, using no processor time
        elif nxt == pc and freeze(sh) == state[1]:  # the step leads straight back to itself and changes nothing
            how = "spins forever on"  # busy waiting that can never end
        else:  # the step can still change something
            how = "can still take"  # (only possible in a stuck state that loops through several states)
        words.append(f"T{t} {how} '{program[pc][0]}'")  # e.g. "T1 spins forever on 'while turn != me: wait'"
    return "; ".join(words)  # both descriptions on one line


def in_cs(program, pc):  # is a thread whose next step is pc inside its critical section?
    return pc < len(program) and program[pc][0].startswith("CS:")  # only steps marked "CS:" count


def check(name, model):  # explores one model and prints what can and cannot happen
    threads, init = model["threads"], model["init"]  # the two programs, and the shared variables' starting values
    came_from, moves = explore(threads, init)  # every reachable state
    states = list(came_from)  # in breadth-first order: a state earlier in the list is fewer steps from the start
    print(f"  {name}: {len(states)} reachable states")  # how big the search was
    done = [s for s in states if all(pc == len(p) for pc, p in zip(s[0], threads))]  # states where both threads have finished
    if "result" in model:  # Experiment 1 only asks which final values are possible
        values = sorted({dict(s[1])[model["result"]] for s in done})  # each distinct final value once, smallest first
        print(f"    possible final values of {model['result']}: {', '.join(map(str, values))}")  # the answer
        return  # nothing else to check
    if not all(any(text.startswith("CS:") for text, _ in p) for p in threads):  # some thread has no step marked "CS:"...
        print("    WARNING: a thread has no step marked 'CS:', so the mutual exclusion check means nothing")  # ...so the next check cannot see it inside
    both_in = [s for s in states if all(in_cs(p, pc) for p, pc in zip(threads, s[0]))]  # states with both threads inside
    if both_in:  # mutual exclusion can fail...
        print("    both threads in the critical section at once: POSSIBLE. The shortest way:")  # say so
        show(trace(came_from, threads, both_in[0]))  # and show how (the first one found is the closest to the start)
    else:  # no interleaving gets both inside
        print("    both threads in the critical section at once: never")  # mutual exclusion holds
    if "broken" in model:  # an extra test of the shared variables (Experiment 3: the buffer's limits)
        bad = [s for s in states if model["broken"](dict(s[1]))]  # states that fail the test
        if bad:  # the test can fail...
            print(f"    {model['broken'](dict(bad[0][1]))}: POSSIBLE. The shortest way:")  # say what went wrong
            show(trace(came_from, threads, bad[0]))  # and how
        else:  # no reachable state fails it
            print("    buffer overflow or underflow: never")  # the limits always hold
    behind = {}  # the moves turned around: for each state, the states that lead into it
    for state, outs in moves.items():  # every state...
        for out in outs:  # ...and every move out of it
            behind.setdefault(out, []).append(state)  # record the move backwards
    can_finish = set(done)  # states from which both threads can still finish; it grows backwards from the finished ones
    queue = deque(done)  # states whose predecessors have not been looked at yet
    while queue:  # walk the moves backwards
        state = queue.popleft()  # a state that can finish...
        for before in behind.get(state, []):  # ...so every state that leads into it can finish too
            if before not in can_finish:  # new
                can_finish.add(before)  # mark it
                queue.append(before)  # and walk back from it later
    stuck = [s for s in states if s not in can_finish]  # reachable states from which finishing is impossible
    if stuck:  # some interleaving traps the threads (deadlock, or spinning forever)
        traps = [s for s in stuck if all(out == s for out in moves[s])]  # stuck states where no step changes anything at all
        end = (traps or stuck)[0]  # show the nearest such trap (or, if there is none, the nearest stuck state)
        where = "a dead end (a state no step can change)" if traps else "a stuck state"  # what the trace below leads to
        print(f"    can always still finish: NO ({len(stuck)} of {len(states)} states are stuck). The shortest way to {where}:")  # say so
        show(trace(came_from, threads, end))  # the moves that lead there (none if the start itself is stuck)
        print(f"      stuck: {status(threads, end)}")  # what each thread is doing there, forever
    else:  # from every reachable state, some order of steps still finishes both threads
        print("    can always still finish: yes")  # no deadlock and no state that spins forever
